# 向上级请求反馈

## 用途

把「上级口头夸过」变成可核验的书面证据，把模糊的职责变成清楚的边界。

请求内容必须是上级容易回答的事实确认，不是要求对方替用户背书。

## 请求前检查

- [ ] 事实已入账，且本人陈述准确；
- [ ] 只请求确认已发生的事，不请求虚构评价；
- [ ] 不请求对方提供不应外传的数据或文件；
- [ ] 一次最多问三件事；
- [ ] 选择合适时机，例如周会后或阶段交付后。

## 可请求的反馈清单

| 类型 | 请求内容 | 得到后的证据等级 |
|---|---|---|
| 职责确认 | 确认本人在某项目中负责的模块 | E2 |
| 交付确认 | 确认某份产物由本人完成并已使用 | E2 |
| 采用确认 | 确认某方案或模板被团队沿用 | E3 |
| 结果口径 | 确认某指标的统计口径与时间范围 | E3 |
| 改进建议 | 指出下一阶段最该提升的一点 | E2 |

## 消息模板

```markdown
<称呼>，打扰一下。

这段时间我主要负责 <模块>，产出了 <交付物>。
想请您确认两件事：
1. 我对自己承担范围的描述是否准确；
2. <交付物> 目前是否还在使用。

另外想请教一句：如果我继续在这个方向上做，您觉得我最该先补的是哪一块？

我会把您的意见记下来，用于自己的阶段复盘。谢谢您。
```

## 阶段结束时的版本

```markdown
<称呼>，我的实习到 <日期> 结束。

这段时间我参与了 <项目>，主要负责 <模块>，产出 <交付物>。
如果方便，想请您用一两句话说明我在其中承担的部分，我会用于个人总结。
如果有不便公开的内容，我不会写进对外材料。

感谢这段时间的带教。
```

## 收到反馈后

1. 原话入账，标注来源、日期与形式；
2. 更新对应事件的 Evidence 与 Evidence Level；
3. 若反馈与本人原描述不一致，以反馈为准修正账本，并写一条更正事件；
4. 若反馈涉及敏感内容，按保密分级处理后再引用。

不得改写上级原话使其更有利，也不得只截取有利片段。
