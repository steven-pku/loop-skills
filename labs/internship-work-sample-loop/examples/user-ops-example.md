# 示例｜用户运营 · 没有数据时降低结论强度

## 输入

JD 原文摘录：

> 用户运营实习生。1）负责沉默用户召回策略设计与执行；2）搭建用户分层体系；3）能独立完成召回效果复盘。

用户诉求：

> 我想做一个召回项目，最后写「召回率提升 20%」这种，简历上好看。

## Scope Gate

`IN_SCOPE`，但用户诉求里包含未来会触发 Fatal 的表述预期，需要在 Phase 1 之前先说清楚。

回应要点：

- 用户没有任何产品的后台数据，也不会有；
- 「召回率提升 20%」需要 E3 证据：真实执行、对照组、前后对比；
- 没有这些而写出百分比就是虚构指标，属于 Fatal，面试官一追问就穿帮；
- 可以替换成同样有说服力、且能答得上追问的表达。

## 结论强度替换

| 用户想写 | 需要的证据 | 实际可得 | 改写为 |
|---|---|---|---|
| 召回率提升 20% | E3，真实执行加对照 | 无 | 设计了一套沉默用户召回方案，定义了可测量的召回指标与证伪条件 |
| 覆盖 10 万沉默用户 | E3，真实用户量 | 无 | 基于公开产品机制与 60 条公开反馈，划出 3 类沉默成因 |
| 验证了分层模型有效 | E3，实验结果 | 无 | 分层模型未执行验证，附验证方案与所需数据清单 |

替换后的表达都能追到 E2 产物，且能回答「你怎么知道」。

## 项目定型

- 项目问题：某社区产品中，注册 30 天后不再发帖的用户，从公开反馈看主要卡在哪三类原因。
- 交付物：抽样规则、60 条反馈编码表、3 类成因归纳、每类对应的召回动作设计、指标定义与证伪条件、未验证清单。
- 结论强度上限：观察与假设，不出现因果与百分比。

## 用人方审查要点

| 检查 | 结果 |
|---|---|
| 结论是否超出证据 | 通过，全文最强表述为「在这 60 条样本中」 |
| 是否有可查看产物 | 通过，编码表、抽样规则、动作设计三项 |
| 是否标注未执行 | 通过，召回动作明确标注「设计方案，未执行」 |
| 用户能否解释编码标准 | 通过，编码表含判定规则与边界样例 |
| 是否伪装任职 | 通过，首屏标注个人独立研究 |

## 面试对照

面试官追问：「你这个召回方案有效果数据吗？」

- 错误答法：编一个数字，或含糊说「效果不错」。
- 正确答法：没有。这是基于公开反馈的设计方案，未执行。我定义了召回率的计算口径和判定它无效的条件，拿到后台数据后第一步是先跑基线。

第二种答法在评审里加分，因为它同时证明了口径能力和边界意识。

## 判决

总分 82，Fatal = 0，通过。停止原因：达标并关闭。

关键点：**降低结论强度提高了通过率，不是降低了作品价值。** 编出来的 20% 会在追问的第二个问题就崩掉，并触发 Fatal。
