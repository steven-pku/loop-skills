# Resume QA Rubric（/100）

> 先按账本 v2 核对原话、来源、角色边界及核验状态。未支持内容被当事实输出才是表达侧 fatal；材料未知先列缺口，不断定用户造假。
> 高分和扣分都须引用简历原句与对应材料。权重及阈值是编辑启发式，未声称统计校准：≥85 且无 fatal＝Pass；82-84＝Borderline；<82 或任一 fatal＝Revise。定向／整稿修订共享两次预算，规则见 SKILL.md。
> 分数是**内部 QA 相对信号**，"Pass" 指「无已识别 fatal + 达 rubric 线」，不预测「这份简历一定能拿面试」（85 分简历在强候选池仍可能落选，冷门岗 78 分也可能够用）。

## 六维评分

### 1. JD 匹配与平台搜索命中 /25

- 23-25：映射矩阵硬需求全覆盖或已声明；技能词与 JD 原词对齐且具体（「PyTorch 实战」而非「机器学习」）；无关键词堆砌感。
- 15-22：主要需求覆盖但表述泛化；部分 JD 原词未对齐。
- <15：与目标岗位错位；关键需求未覆盖也未声明。
- 注意：命中靠**真实技能的具体化表述**，不靠埋点堆词。与经历无关的关键词＝真实性问题，转 fatal 审计。

### 2. 成果证据 /25

- 23-25：主要条目有具体动作及有来源支持的结果；定量、具体定性或真实失败都可成立，且个人动作与团队结果分开。全篇定性不自动扣分。
- 15-22：部分条目有结果，关键条目仍只有职责或结果依据不清。
- <15：通篇动作无具体结果；“效果很好”不构成结果证据。
- 定性锚点：用户原话“我整理了提交前核对清单，清单被团队采用”，且提供采用记录，可支持这一描述；没有频次、比例或收益数字也可高分。不能由采用推成减少错误或提高效率。
- 量化锚点：用户提供前后数据、口径与本人角色时可写变化；没有来源的数字不会因精确而得分。真正失败可按实际代价及动作呈现，不能补成成功案例。

### 3. 事实保真 /15

- 13-15：所有事实来源可定位；原话限定、程度、因果、角色边界及核验状态保留；推算单位与输入齐全。未独立核验明确披露，不被改写成已证实。
- 8-12：出处／角色边界有待澄清，或表达强度需要降低；这是材料或表达问题，不是对候选人诚信下结论。
- <8：输出将无来源或增强后的内容写成既定事实，触发表达侧 fatal；若只是缺材料，先追问或删除主张，不能用未知本身判造假。

### 4. 结构与信息密度 /15

- 13-15：一页纪律达标（应届/5 年内）；倒序；当前角色权重最大；无关经历已裁剪。
- 8-12：结构对但密度失衡（老经历占比过大 / 项目罗列不分主次）。
- <8：时间线混乱或无关经历占主体。

### 5. 语言 /10

- 9-10：动词具体有力；无空话（精通/熟悉/参与/协助 滥用）；句式紧凑。
- 6-8：个别空话；动词弱（「进行了」「参与了」）。
- <6：通篇职责腔。

### 6. 筛读友好 /10

- 9-10：首屏动线顺（当前角色/公司 → 时间连续性 → 教育背景一眼可得）；版式无噪声。
- 6-8：关键信息在但动线绕。
- <6：初筛 scan 抓不到定位。
- 依据分级：英文简历眼动报告仅给版式启发，见 evidence-notes.md 的来源与范围；不承诺中文招聘的固定秒数或普适扫描顺序。

## Fatal issues（一票 Revise）

1. 编造经历或数字（含〔待补数据〕被填成实数、账本外条目）
2. 有限澄清后仍没有任何具体、有来源支持的结果；仅无数字不触发，定性采用、作品或真实失败均可作为结果
3. 无关经历占主体
4. 空泛技能罗列（「精通 X」背后无经历支撑）
5. 有限澄清后仍无法读出岗位相关经历的基本时间顺序；空档本身不是诚信 fatal，也不要求披露私人原因
6. JD 硬需求未覆盖且未进「无法覆盖」声明

## 修订规则要求

坏例：「提高量化程度」。
好例：「E02 的『负责提交管理』按用户提供的采用记录改成『整理提交前核对清单，并被团队采用』；不补减少错误率或节省时长。数字确有原始数据时才按账本填写」。
