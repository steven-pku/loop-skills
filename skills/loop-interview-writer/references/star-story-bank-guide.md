# STAR 故事库构建

## 从账本到故事

1. 每个账本条目（E{NN}）按「可讲的故事角度」拆出候选故事——一个条目可出多个故事，一个故事只锚定一个主冲突。
2. 故事骨架：S／T 合并简述 → A＝本人实际动作及角色边界 → R＝账本 v2 的定量、具体定性或真实失败结果，保留来源与核验状态。
3. **R 准入线**：要有具体支持；采用记录、行为变化或失败代价均可，不强求数字或后续成功。只有“学到了很多”不够，按共同预算追问或换角度；未满足的故事列缺料，不编造入库。非故事型答案不用本故事模板。

## 故事 × 题型映射表

```markdown
| 故事 | 来源条目 | T2 项目深挖 | T3-冲突 | T3-失败 | T3-压力 | T3-团队 | 备注 |
|---|---|---|---|---|---|---|---|
| 支付模块重设计 | E04 | ◎ 主用 | | | ○ 可用 | | 90s 版+3min 版各备 |
| 跨部门数据打通 | E02 | ○ | ◎ 主用 | | | ○ | 冲突落点在推进机制 |
```

- ◎ 主用 / ○ 备用；一场面试同一故事只讲一次——映射表就是防重复调度表。
- 按用户请求检查题型覆盖。缺格如实列出，只在材料和澄清预算允许时再挖；不为填满表格重复、编造或无限追问。

## 故事卡（交付格式）

用 `assets/story-card-template.md`。每卡含：一句话版（钩子）/ 90 秒版（默认应答）/ 3 分钟版（深挖展开）/ 追问预案（该故事最可能被追的 2-3 个点及答法）。

## 失败故事特别规则

- 必须有真实失败事实和代价。“我太追求完美”但缺事实时是材料不足／题意未答，不等于已经证实编造；追问或换故事。明确要求伪造失败才拒绝。
- 结构：失败事实 → 当时的错误判断 → 代价 → 之后**做法层面**的改变（不是态度层面）→（如有）后续验证。
- 失败故事的 R 首先是实际失败及代价；后续具体做法变化和验证有材料才加。没有后续成功也可诚实描述，不把未验证改进写成已产生收益。
