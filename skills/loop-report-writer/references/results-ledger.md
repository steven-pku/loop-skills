# 成果账本（results ledger · schema v1）

> 账本是全 skill 的事实地基：汇报里写的每个成果、每个数字，都只能来自这里。
> 结构沿 Loop 系列求职双件的 career-facts ledger 简化（自包含，无跨仓依赖）。

## Schema

```markdown
# Results Ledger · {姓名/周期} · ledger-schema v1

## 成果条目 A{NN}
- 动作（做了什么）：
- 结果（改变了什么，可被感知的变化）：
- 量化点：{描述} = {数值或〔待补数据〕}
  - 来源标注（三选一，必填）：用户提供 / 合理推算（依据：…）/ 〔待补数据〕
- 对读者的意义：（读者拿这条做什么判断——继续投入 / 调方向 / 升职背书 / 风险预警）
- 关联场景：（周报条目 / 述职案例 / 晋升答辩证据链）
```

## 账本纪律（不可妥协）

1. **条目只能来自用户输入**。转述允许，无中生有禁止。
2. **量化点三选一来源标注**：
   - 用户提供：原话或原始材料里有。
   - 合理推算：从用户给的数据能算出来（写明推算式，如「本人处理一单从 12 分钟降到 8 分钟 × 日均 30 单 × 22 天 ≈ 每月省约 44 小时」）。**推算对象必须对应所声称的成果主体**：个人汇报里推算个人贡献，团队总量（「5 人 × 22 天」）不得当成个人成果写入——要写团队量就明写「团队」，别弱化成个人功劳（呼应 achievement-rewrite-patterns P5）。
   - 〔待补数据〕：该有数字但用户没给——保留标记，进追问清单。
3. **〔待补数据〕禁止在任何成稿中变成具体数字**。QA 真实性审计逐条核对。〔待补数据〕条目在成稿中允许两种形态：保留标记（内部稿）或改用具体的定性表述（「上线后客服重复咨询明显减少〔量化待补〕」）。
4. **甄别依据，拒编造与注水（先追问，再定拒或转）**：用户给「大概 30%」「差不多提升一半」这类模糊数字，或要求注水凑字数（「帮我写满 800 字」）时——
   - **模糊数字先追问依据**：「这个数怎么来的？」
     - **能陈述可复现依据**（看过后台 / 能从已知数据算出，如「活动首日销售额约平时 1.3 倍」）→ 转「合理推算」档：写明观测来源或推算式后可写入，标注为合理推算，**这不是编造**。甄别依据正是本 skill 该做的动作，不是一刀切拒。
     - **纯感觉 / 为了好看 / 拿不出依据** → 拒绝该目标，一句话说明边界（「本 skill 只做真实成果的价值挖掘，不编造数字」），保留〔待补数据〕或改具体定性表述。
   - **注水凑字数**：直接拒 + 替代（换成果角度——一件事对不同读者有不同价值面 / 如实短汇报，少而真好过长而水）。
   - 不做「念一遍免责声明然后照写」。
   - **能力边界（诚实声明，勿夸大）**：「甄别依据」验证的是用户**能否陈述一个可复现的依据**，不是依据**本身为真**——skill 审计不了用户的后台数据，一个想注水的用户编一句「我看过后台，首日 1.3 倍」，skill 无法证伪，会照「合理推算」档写入。因此本 skill 保证的是**可溯源 + 诚实标注**（读者能看到这是推算及其口径），**不保证用户陈述的依据属实**。别把它宣称成「防造假」的真值校验。

## 追问清单模式

缺量化数据时，生成**具体到可直接回答**的问题，而不是「请提供更多数据」：

```markdown
## 素材追问清单（回答后账本自动升级）
1. A02 的流程优化：处理一单的时间从多少降到多少？覆盖多少人/单量？
2. A03 上线的功能：30 天内转化率/使用量/工单量相比之前变化多少？
3. A05 你提的方案被采纳后：省了多少预算/工时？谁在用？
```

- 问题上限一次 5 条，按「对本次汇报读者的重要性」排序。
- 追问后仍无数据 → 保留〔待补数据〕，用具体定性表述兜底；**绝不发明数字**。

## 与在职汇报的特有约定

- 账本按周期滚动：周报账本可聚合成月报/季度账本；述职/晋升答辩从多周期账本中选证据链。建议用户保存账本文件复用。
- **进行中事项也入账本**：动作＝推进到哪个里程碑，结果＝当前可核验状态（「联调完成 80%，阻塞在 X」），不许写成已完成。
- 团队成果与个人贡献分开记（「5 人小组中我负责缓存层」），述职深挖不穿帮。
